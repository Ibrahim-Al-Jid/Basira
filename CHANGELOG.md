# Changelog

## 2026-11-28

### Fixed
- Custom provider connections are pinned to the address that was checked (#158). Root cause: the host was checked when the request was built and resolved again at connect time, so a DNS answer that changed in between (DNS rebinding) could reach a private address. `llm_providers.pin_request` now resolves once, requires every address to be public, and connects to one of them with the original Host header and TLS server name.
- Password sign-in looked up the wrong account: `basira_login_identity` returned a row for every user, so a login was compared against whichever row came back first. Root cause: in a SQL function the unqualified `issuer` and `subject` resolved to the table's columns, so the filter compared each column with itself. Migration 0032 qualifies them with the function name, and `backend/test_postgres_schema.py` checks the function returns only the requested identity. A password that matched the wrong account would have been accepted; legitimate logins were being rejected.
- Scan idempotency keys are scoped to one project. The unique constraint on `project_scans` spanned the whole organization while the API looked the key up per project, so reusing the same `Idempotency-Key` in a second project of the same organization returned 409 "the key is linked to a different request" instead of creating the scan. Migration `platform_idempotency_0017` replaces `uq_project_scans_request` with `uq_project_scans_project_request` on (org, project, user, key). Reproduced and re-checked on PostgreSQL 16 with the `basira_app` role: before, 409; after, 202 in both projects.
- Scan idempotency keys are scoped to one project instead of the whole table.
- Sessions: every request without a cookie inserted a row and expired rows were never deleted.
- Report schema: the DDL ran in the per-request connection helper, so reads took a write lock; it is now prepared once per process.
- HAR coverage: "could not look" was stored as "does not apply", so a HAR without complete headers came back clean.
- App shell headers: the full set (CSP, framing, referrer policy) was set only for `/api/`, so the app page had none.
- Dispatcher: inline delivery wrote to the database the dispatcher held open, so SQLite said "database is locked"; a dispatched job is now delivered after the claim transaction commits.
- Source languages: "cannot parse this file" was stored as "does not apply", so a Go-only ZIP reported completed with no findings.
- Configuration document review: `prepare()` assumed every configuration artifact is a `{"files": ...}` package, so a plain document was rejected before any rule ran.
### Added
- Hunter tool loop (P4): `backend/hunter_loop.py` runs a bounded loop with an injected model callable, an allow-list of tools (`search_code`, `read_file`, and `run_rules` in hybrid), step, tool-call, token and time budgets, and tool output wrapped as untrusted data. Candidates pass through the Auditor check. Any failure returns a fixed status (`disabled`, `model_error`, `invalid_output`, `budget_*`) and no candidates, so the caller keeps the deterministic result. The module checks `BASIRA_AGENT_LOOP=1` itself. The gateway and worker calls are in #167 and #166 below; run modes stay planned, not shipped.
- CI runs the personal-projects browser suite on every pull request (#152), in the personal-mode job after the browser smoke. Before this it ran only when someone ran it by hand.
- CI runs the password-login browser suite on every pull request, alongside the account and workspace suites: signup, sign-in and cross-account isolation with password auth on.
- Auditor candidate check: `backend/auditor.py` accepts a proposed candidate only if it points at a real path and line in the pinned snapshot and quotes what is there, re-reading the files rather than trusting the model. Rejections carry a fixed reason code (`bad_shape`, `unknown_path`, `line_out_of_range`, `quote_missing`, `quote_not_at_location`, `unknown_rule`, `duplicate`), never model text. Not called from a scan yet; P4 wires it in.
- Project map: `backend/project_map.py` builds the Scout's map of a submitted snapshot deterministically, with no model, network or file bodies: languages with file counts, entry points, routes with method and path, config files, dependency manifests, and trust boundaries (database, file upload, outbound HTTP, process execution, auth). Same input gives the same map, and the map holds paths and counts only, so it is safe to store. It is not called from a scan yet; P4 wires it in.
- Lab reports made before sign-in could be claimed from the project reports archive ("Lab reports in your session" panel). That panel was removed in #178 together with the reports page's `/api/reports` fallbacks, as the anonymous-lab flow is retired. The claim endpoint `POST /api/platform/projects/{project_id}/reports/{report_id}/claim` is unchanged; no screen calls it now. Not run: a browser check of the claim endpoint after the removal.
- Anonymous lab runs are guarded: `POST /api/run` allows 30 runs per client IP in a fixed 15-minute window (`BASIRA_LAB_RUN_LIMIT`) and 8 in flight per process (`BASIRA_LAB_RUN_CONCURRENCY`), answering 429 with `Retry-After` over either limit. Root cause: the model budget check only covered the platform scan path, so any unauthenticated client could start unlimited lab runs, each holding a worker for up to 300 seconds and spending shared model quota.
- Agent memory tables in the schema: `project_maps`, `scan_agent_runs` and `scan_agent_steps`, alongside `analysis_mode` on the scan. Root cause: the design needs a project map and a per-step record before the agent path can run, and there was nowhere to store either, so a model-backed step could not be audited afterwards.
- Entry page: a procedural WebGL planet with a canvas-globe fallback, reduced-motion handling and below-the-fold sections in English and Arabic. The planet textures are NASA-derived imagery shipped by the `three-globe` package; the README credits it. Root cause: the first page explained nothing about the product and had no visual anchor.
- Scan run modes are documented with their acceptance criteria and left unimplemented: rules (today's deterministic chain), agents, and hybrid, with `analysis_mode` defaulting to `rules` when the schema and the loop land. Root cause: the design was in one long architecture note, so the modes and what would make each one acceptable were not written down separately.
- Source intake suite: its Dockerfile moved out of the build directory the scan test exercises, so the fixture no longer appears as a scanned file. Root cause: the suite lived under a path the new configuration scan reads, so the fixture changed its own result.
- Container operations: every service and the database and broker log through the `json-file` driver capped at 10 MB times 3 files, the `app` service has a healthcheck and the image has a `HEALTHCHECK`, so a hung process is restarted or routed around instead of looking up. `app`, `worker`, `dispatcher` and `model-gateway` run with `cap_drop: [ALL]` and `no-new-privileges`, which they do not need (they already run as an unprivileged user); the scanner keeps its own isolation.
- The image build runs `pip check` after installing the requirements and sets `PYTHONDONTWRITEBYTECODE=1`; `.dockerignore` keeps `tests/`, `docs/` and `backend/test_*.py` out of the build context and the runtime image.

The stable id stays what rows and contracts store. Root cause: the interface and the docs described the pipeline by function only, so a person reading a report could not name the agent that produced a step.

Root cause: the first page assumed you already had an account and explained nothing about the product.

Root cause: uvicorn ran with `--no-access-log`, so the app kept no record of who asked for what or how long it took.

Root cause: nothing checked the repository itself, the image was never built in CI, and the schema tests never ran against the database they deploy to.
- Platform backup and restore verification: `ops/backup-platform.py` dumps with `pg_dump -Fc` and proves the archive with `pg_restore --list`, and `ops/verify_restore.sh` restores into a scratch database and compares shape (tables, policies, functions, tables with row level security, `alembic_version`) and posture (`basira_app` grants, definer functions executable by PUBLIC) against the source. Root cause: the runbook was manual and nothing proved a dump was readable or that a restore kept its policies, so a restore could hand one tenant another tenant's rows silently.
