# Changelog

## 2026-11-28

### Fixed
- Scan idempotency keys are scoped to one project. The unique constraint on `project_scans` spanned the whole organization while the API looked the key up per project, so reusing the same `Idempotency-Key` in a second project of the same organization returned 409 "the key is linked to a different request" instead of creating the scan. Migration `platform_idempotency_0017` replaces `uq_project_scans_request` with `uq_project_scans_project_request` on (org, project, user, key). Reproduced and re-checked on PostgreSQL 16 with the `basira_app` role: before, 409; after, 202 in both projects.
- Scan idempotency keys are scoped to one project instead of the whole table.
- Sessions: every request without a cookie inserted a row and expired rows were never deleted.
- Report schema: the DDL ran in the per-request connection helper, so reads took a write lock; it is now prepared once per process.
- HAR coverage: "could not look" was stored as "does not apply", so a HAR without complete headers came back clean.
- App shell headers: the full set (CSP, framing, referrer policy) was set only for `/api/`, so the app page had none.
- Dispatcher: inline delivery wrote to the database the dispatcher held open, so SQLite said "database is locked"; a dispatched job is now delivered after the claim transaction commits.
- Source languages: "cannot parse this file" was stored as "does not apply", so a Go-only ZIP reported completed with no findings.
- Configuration document review: `prepare()` assumed every configuration artifact is a `{"files": ...}` package, so a plain document was rejected before any rule ran.
### Added
- Scan run modes are documented with their acceptance criteria and left unimplemented: rules (today's deterministic chain), agents, and hybrid, with `analysis_mode` defaulting to `rules` when the schema and the loop land. Root cause: the design was in one long architecture note, so the modes and what would make each one acceptable were not written down separately.
- Source intake suite: its Dockerfile moved out of the build directory the scan test exercises, so the fixture no longer appears as a scanned file. Root cause: the suite lived under a path the new configuration scan reads, so the fixture changed its own result.
- Container operations: every service and the database and broker log through the `json-file` driver capped at 10 MB times 3 files, the `app` service has a healthcheck and the image has a `HEALTHCHECK`, so a hung process is restarted or routed around instead of looking up. `app`, `worker`, `dispatcher` and `model-gateway` run with `cap_drop: [ALL]` and `no-new-privileges`, which they do not need (they already run as an unprivileged user); the scanner keeps its own isolation.
- The image build runs `pip check` after installing the requirements and sets `PYTHONDONTWRITEBYTECODE=1`; `.dockerignore` keeps `tests/`, `docs/` and `backend/test_*.py` out of the build context and the runtime image.
- Documentation set for running and operating Basira, in English, with every command checked against `main` on 28 November 2026 (Linux, Python 3.13.18, Node 22.23.5): `docs/SETUP.md` (the three run modes, Windows `ops/start-local.ps1`, `bash ops/start-local.sh` on Linux and macOS, Docker Compose, the model gateway, the GitHub App, where data lives, the five agents, backup and restore, and a per-item record of what was and was not run), `docs/CONFIGURATION.md` (every `BASIRA_*` variable with its default and effect, the two separate GitHub paths, the gateway and the limits it enforces), `docs/API.md` (every path and operation from `app.openapi()`, cookies, `Idempotency-Key`, `/intake/zip` headers, error codes) and `docs/TROUBLESHOOTING.md` (lab 404s under `BASIRA_PERSONAL_PROJECTS=1`, origin mismatch, gateway unavailable, Docker problems). Root cause: the README stopped at `npm start`, so the Windows script, Compose, the gateway and the GitHub App had no written procedure and every setting had to be read out of the code.
- The five agents have names people read: Maestro (orchestrator), Scout (planning), Hunter (analysis), Auditor (validation) and Scribe (reporting), with Arabic names, from one registry in `backend/agent_roles.py`. The stable id stays what rows and contracts store. Root cause: the interface and the docs described the pipeline by function only, so a person reading a report could not name the agent that produced a step.
- Public entry page at `/` with Sign in and an animated globe, and the demo overview moved to `/overview`, plus a procedural WebGL planet with a canvas-globe fallback, reduced-motion handling and below-the-fold sections (what Basira does, how it works, trust, call to action, footer) in English and Arabic. Root cause: the first page assumed you already had an account and explained nothing about the product.
- Access log (`backend/observability.py`): one line per request with a request id, method, path without its query string, status and duration, an `X-Request-ID` response header, and `BASIRA_LOG_LEVEL` to set the level. Root cause: uvicorn ran with `--no-access-log`, so the app kept no record of who asked for what or how long it took.
- CI repository job (`.github/workflows/ci.yml`): `ruff` with defect-only rules, `pip check`, a `gitleaks` scan of the full history with the binary pinned by checksum, and `concurrency` so a superseded push cancels its own run; a container job that builds the image, starts it and waits for the app to answer; a PostgreSQL 16 job for the schema tests; browser smoke tests; `.github/dependabot.yml` for weekly grouped updates and `ruff==0.15.7` pinned. Root cause: nothing checked the repository itself, the image was never built in CI, and the schema tests never ran against the database they deploy to.
- Platform backup and restore verification: `ops/backup-platform.py` dumps with `pg_dump -Fc` and proves the archive with `pg_restore --list`, and `ops/verify_restore.sh` restores into a scratch database and compares shape (tables, policies, functions, tables with row level security, `alembic_version`) and posture (`basira_app` grants, definer functions executable by PUBLIC) against the source. Root cause: the runbook was manual and nothing proved a dump was readable or that a restore kept its policies, so a restore could hand one tenant another tenant's rows silently.
### Fixed
- Report "technical" tab no longer blanks the whole page: `ToolRuns` (frontend/src/ReportAdvanced.jsx) called the translation object as a function (`t("...")`), throwing on every report that shows tool execution. The copy now uses the component's own bilingual strings like the rest of the file.

### Changed
- Row level security and definer functions cover the whole tenant boundary, not part of it: users, memberships, organizations, project grants, projects, invitations, sessions, password credentials, the ownership review queue and the dispatch queue each resolve through a definer function or a policy scoped to the organization that owns the row, and the schema is prepared once per process instead of per request. Root cause: several tables had no policy or resolved their owner through a query that row level security then hid, so a row could be read across tenants or not at all.
- `docs/PLAN.md` re-verified against `main`: the merged-pull-request list and several phase statuses had stopped at #42 while #43 onward had merged, so the plan described work as open that was done. The list now runs to the last merged number and the owner decisions are recorded with the times they were given.
- Every direct dependency pinned to an exact version instead of a range (`requirements.txt`). Root cause: range pins let a rebuild install a different set than the one that was tested.
- Container operations: services log through the `json-file` driver capped at 10 MB times 3 files, every service has a healthcheck (`app` and the image by HTTP, `worker` through `celery inspect ping`, `model-gateway` through a bearer `/health`, `dispatcher` and `scanner` by reading `/proc/1/cmdline`), and `app`, `worker`, `dispatcher` and `model-gateway` run with `cap_drop: [ALL]` and `no-new-privileges`. Root cause: unbounded logs could fill the disk and take the database with them, and a hung or crash-looping service looked the same as a healthy one in `docker compose ps`.
- The model gateway caps what a user-chosen provider address can return: 4 MiB for a catalogue, 256 KiB for a reply, and it refuses more than twelve evidence items or three planning hints. Root cause: the provider address is user-supplied, so an unbounded response could exhaust memory.
- Three ways to run it locally are in one place: the lab with `npm start`, the Windows one-command stack (`ops/start-local.ps1`) and Docker Compose, with `bash ops/start-local.sh` for Linux and macOS. Each has its own prerequisites, and the page states which steps were run here and which were not.

### Planned, not implemented
- The analysis modes are designed, not built. `docs/ARCHITECTURE-agents.md` records the decision (hybrid: deterministic rules and scanners as tools, agents planning and proposing candidates, a validator that re-checks evidence) and the five configurations it will be measured on (C1 rules, C2 one agent, C3 team, C4 team with tools, C5 hybrid with a validator), with the order to build them. What runs today is the deterministic chain of five roles with one validated model call after analysis that only reorders priorities. `docs/ARCHITECTURE.md` describes an orchestrator that chooses split or combined analysis; the code does not do that yet, and that page says so.
